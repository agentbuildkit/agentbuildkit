# 0.2.0 publication checklist

Published on 22 November 2026: PyPI `agentbuildkit` 0.2.0, PyPI `agentbuildkit-templates` 0.2.0, and npm `agentbuildkit` 0.0.3. The checklist below is the record of that release. A later release uses new version numbers and a new validation run.

Do not publish from a branch push, a pull request, a merge, or a GitHub Release. `.github/workflows/release-validate.yml` builds and tests a candidate. `.github/workflows/release.yml` is the only workflow that can publish, and only from `workflow_dispatch`.

Typing a stage name selects the job. It is not an approval. The publish jobs use the GitHub environments `pypi`, `pypi-templates`, and `npm`. Each of those environments allows deployments from `master` only. This GitHub plan does not support required reviewers, so the environment does not add a separate reviewer prompt. Dispatching the workflow on `master` is the manual gate. The verification jobs do not publish and do not use those environments.

## Candidate artifacts

Validation uploads one immutable artifact named `release-candidate`. GitHub keeps it for 14 days. It contains the two wheels, the two source distributions, `agentbuildkit-0.0.3.tgz`, and `manifest.json`. The manifest records the full source commit, the workflow run id, the workflow filename, and the SHA-256 of each file.

Retrieve it with:

```bash
gh run download RUN_ID --repo agentbuildkit/agentbuildkit --name release-candidate
```

Publication downloads that run and refuses the job when the run failed, came from another workflow, belongs to another commit, or the file bytes do not match the manifest. It does not build again. A missing or expired artifact stops the job. Create a new candidate by running Release validation on that commit.

The trusted publishers must name the workflow file `release.yml`. They must not name `release-validate.yml`. The validation workflow has no `id-token` permission and cannot mint a registry token.

## Before the first publication stage

- [ ] Record the merge commit and the successful Release validation run id.
- [ ] Confirm the manifest commit is that merge commit and the checksums match the uploaded files.
- [ ] Confirm CI on Ubuntu passed for that commit. A local macOS run does not replace it.
- [ ] Confirm `agentbuildkit` 0.2.0, `agentbuildkit-templates` 0.2.0, and npm `agentbuildkit` 0.0.3 are still unpublished.
- [ ] Confirm each trusted publisher below. The environment name alone does not authorize a workflow.

## Trusted publishers

PyPI binds the GitHub owner, repository, workflow filename, and environment. npm binds the same fields and also requires `repository.url` in `package.json` to match the GitHub repository. This repository is `agentbuildkit/agentbuildkit`. The workflow filename is `release.yml`.

| Package | Owner | Repository | Workflow file | Environment |
| --- | --- | --- | --- | --- |
| PyPI `agentbuildkit` | `agentbuildkit` | `agentbuildkit` | `release.yml` | `pypi` |
| PyPI `agentbuildkit-templates` | `agentbuildkit` | `agentbuildkit` | `release.yml` | `pypi-templates` |
| npm `agentbuildkit` | `agentbuildkit` | `agentbuildkit` | `release.yml` | `npm` |

The first publish of `agentbuildkit-templates` 0.2.0 created that PyPI project. A pending publisher does not reserve a name until the first publish.

npm trusted publishing requires Node.js 22.14 or newer and npm 11.5.1 or newer. The publish job installs Node.js 22. On npm, allow `npm publish` for this publisher. A new npm publisher must complete its first publish within two days or it expires. Create it when the npm stage is about to be approved, not earlier. Do not create a long-lived token.

No registry token is stored in this repository.

## Publication order

Dispatch Release on `master` at the validated commit. Pass the validation run id. Approve the GitHub environment when it is requested. Do not approve a different stage in the same dispatch.

1. `publish-harness`, confirm `publish-harness`, environment `pypi`.
2. `publish-templates`, confirm `publish-templates`, environment `pypi-templates`. This stage requires the published harness files to match the candidate.
3. `verify-python`, confirm `verify-python`. This installs the public pair and does not publish.
4. `publish-npm`, confirm `publish-npm`, environment `npm`. This publishes the validated tarball after both Python packages match.
5. `verify-npm`, confirm `verify-npm`. This compares the public tarball and runs `npx --yes agentbuildkit@0.0.3 --help`. It does not publish.

## Partial publication

The two Python uploads are not one transaction.

- If a version is absent, that stage may upload the validated files.
- If every filename and SHA-256 matches the candidate, the stage resumes without uploading.
- If any filename or digest differs, the stage stops. Do not overwrite the version and do not treat it as done.
- If the harness is published and the templates upload fails, the harness-only install still works. Do not publish npm until the templates files match the candidate.
- If both Python packages are published and npm fails, the Python pair can still be installed directly. npm 0.0.2 remains the older harness-only bootstrapper. npm 0.0.3 is the current bootstrapper.

## If a published release is defective

PyPI and npm do not allow replacing the files of a published version. Choose a new version, such as 0.2.1 for Python or 0.0.4 for npm. Yank the defective version only as a resolver warning, and say so in the recovery notes. Do not assume the bad files can be overwritten.
